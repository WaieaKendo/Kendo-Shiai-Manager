# KSM roadmap and task list

## How branches work

- **`develop`** holds all finished, tested work. Every new task branches from `develop` and is merged back into it once `npm test` passes and it has been reviewed, so each new branch starts with everything done so far.
- **`main`** only moves at release points (after sign-off, and never inside the pre-event freeze): `develop` is merged into `main`.
- Task branches are short-lived: `fix/…`, `feat/…`, `test/…`, `refactor/…`, `docs/…`. After merging they can be deleted — their commits live on in `develop`.
- If a task needs another unfinished branch's work, merge that branch into `develop` first, or `git cherry-pick` the specific commit.
- Golden snapshot conflicts (two branches both changed `tests/golden/engine/*.json`): merge, then run `npm run test:golden:update`, review the diff, and commit.
- Golden snapshot changes are always reviewed in the diff and explained in the commit message.

### M.9 Path URLs: plan

Today every screen is one page driven by query parameters (`/?tournament=<id>&court=A`, `&role=spectator&view=tv` for a TV); only the stream overlay has a path (`/overlay`). After M.8, move to path URLs, for example `/t/<id>/court/a`, `/t/<id>/tv/a`, `/t/<id>/live`, `/t/<id>/overlay/a`. Routing is its own step, not part of the React conversion. To handle:

- **Existing links**: TV, court and overlay links are copied onto devices before an event. Old query links must keep working, most likely by redirecting to the new path.
- **Offline**: the service worker serves only `/` and `/index.html` as the app shell and sends every other navigation to the network. It must serve the app for the new paths, or an offline court device gets nothing.
- **Hosting**: Cloudflare must answer the new paths with the app, as it maps `/overlay` to `overlay.html` today.
- **Passwords in links** (Phase 3: logins, device pairing): design the URL scheme together with that, so links change only once.
- **Tests**: `KsmApp.open_device` paths, the TV/overlay link tests and `e2e-full` use the query links; add the new paths and keep one check that the old links still work.

**Done (`feat/path-urls`).** The scheme (`app/engine/routes.ts`; court letters lowercase, the ID percent-encoded):

| Path | Screen | Old link (still works: replaced by the path) |
|---|---|---|
| `/` | Tournament Library (home) | `/` |
| `/t/<id>` | Live Scores as a spectator, on the court this device chose before | `/?tournament=<id>`, `/?spectator=<id>`, `/index.html?tournament=<id>` |
| `/t/<id>/live` | the same, by name | — |
| `/t/<id>/court/a`, `/court/b` | a court device: as `/t/<id>`, assigned Court A/B (the court screen opens on it) | `/?tournament=<id>&court=A` |
| `/t/<id>/tv/a`, `/tv/b` | TV display for Court A/B | `/?role=spectator&tournament=<id>&court=A&view=tv` (also without `role`, and `&view=tv` without a court = Court A) |
| `/t/<id>/overlay/a`, `/overlay/b` | stream overlay page (`overlay.html`); options `red`, `pos`, `y`, `band`, `debug` stay query parameters | `/overlay?tournament=<id>&court=A&…` |

Decisions:
- **The path says what the link said, not which screen is open.** In-app navigation (menus, Courts → Court B, Results) does not change the address, as before (no new history entries; back/forward and reload behave as they did with the query links). A court link still lands on Live Scores and staff open their court from the Courts menu, as before; `/t/<id>/court/b` assigns Court B as `&court=B` did. Making the address follow the open screen (and the library's open tournament) is a behaviour change left for later.
- **Short and odd forms**: `/t/<id>/tv` and `/t/<id>/overlay` mean Court A (as the old links without `&court=`), `/t/<id>/court` means `/t/<id>`; uppercase and a trailing slash are tidied (`replaceState`). Any other `/t/...` path is replaced by `/` and shows the Tournament Library (an unknown tournament falls back to it too, as it did; its path stays, so a reload retries).
- **Old links**: turned into paths in the browser (first thing `app.js` and the overlay page do), so it also works offline from the service worker's copy; other parameters are kept as they were. `role=spectator` is dropped (every link opens as a spectator); `role=` other values and `key=` stay query parameters on the path. The app adds `key=` only to the TV link of a device still holding an old per-role credential (`cloudSession.credentials`, from before v3.16), and nothing reads it since v3.16; it is kept on the path as before, and removing keys from links waits for the login decision (#9).
- **Hosting**: Cloudflare's single-page fallback answers every `/t/...` path with `index.html`; `run_worker_first` sends `/t/*` to the Worker, which answers `/t/<id>/overlay/…` with `overlay.html` (as `/overlay`). The custom-domain pass-through (PR #20) forwards every path, so it needs nothing. The service worker serves its offline copy of the app for `/`, `/index.html` and `/t/...` except the overlay (live-only, as `/overlay`). The Vite dev server rewrites the overlay path the same way.

### M.10 Sync safety net: plan

Today only the TV has a fallback for a missed live update (full refresh every 15 s, on a revision gap and when it becomes visible). Scorekeepers, spectators and the overlay (`useTournamentRecord`) rely on the socket and its reconnects. Add one safety net in `useTournamentRecord`, so every React page has it:

1. **Revision-only check** (first piece): a tiny endpoint returning the latest revision, or an ETag/`If-None-Match` GET answered 304 when nothing changed. Download the full record only when the revision is newer. Add jitter so devices do not ask at the same second.
2. **Pace by socket health first**: socket healthy → every 30–60 s; socket down or reconnecting → every 5–10 s with backoff until it is back.
3. **Pace by tournament phase**: before generation → none; live → as above; after the last match (from the engine's completion data, not a UI rule) → every few minutes, because results often get corrected after the final; archived → none.
4. **Always check at once** when the page becomes visible, when the network comes back and when a socket message skips a revision (as the TV does today).
5. **Staff devices**: a polled record follows the socket rule: while the device has unconfirmed local changes it is deferred, never applied over them (see F6).

With action-based sync (Phase 3) the same check becomes "actions after revision N".

### M.11 Per-tournament theming: plan

Rules for the structural steps:
- **Colors only through theme tokens**: CSS custom properties (today's `:root` set in `app/styles/02-branding.css`: `--ksm-navy`, `--ksm-gold`, …). No new hard-coded colors in React components or new CSS; when a step rewrites CSS, it replaces the hex values it touches with tokens (about 430 remain today; the overlay CSS has its own).
- **Assets from one place**: logos, watermark and background images come from one theme module / prop with today's KSM assets as defaults, never inlined in markup, so a tournament's images can replace them.
- **Kendo semantics stay fixed**: red/white side colors and completed/live states are meaning, not branding; a theme may tint accents, not swap aka/shiro. Keep contrast readable on the TV and in print.

M.11 itself:
1. **Theme data**: a `branding` object in the tournament's setup (colors, asset references), read through a typed accessor with KSM defaults (like `readSettings`), applied once at the page root as CSS variables. Synced like other setup data.
2. **Images as separate assets, not inside the snapshot**: v3.16.2 stored the logo as PNG data in the setup snapshot and v3.17.3 removed it (the Worker strips it), because the snapshot is re-sent on every save. Store images in R2 (or another asset store) by content hash, reference them from `branding`, cache them in the service worker for offline devices.
3. **Setup editor**: pick colors (with a contrast check), upload/remove images, preview on court/TV/overlay; reset to KSM defaults.
4. **Print**: printed sheets use the logo and a print-safe variant of the colors.
5. **Tests**: themed and default tournaments through the layout/parity tests; contrast check on TV and court.

### 1.9 Match timer, match-end confirmation and sound: plan

One feature, because the clock and the scoring both feed the same question: is this match decided? The engine already knows the rules (`winnerOf`, `matchRequiresWinner`); the screen asks it after every point, hansoku and time-up and never copies the rules.

**Match timer**
- Built on 1.5: each stage's match length, encho rule (unlimited or fixed) and tiebreak/representative bout length.
- One clock per court, run by that court's scorekeeper device. TV and overlay receive "started at X with 2:31 left" / "paused at 2:31" and count down locally; one small sync message per start or stop, never a save per second (today's sync sends the whole tournament on every save).
- Kendo rules: start/stop on yame; optional auto-pause when a point is scored (per tournament); a separate injury/time-out pause; at time-up the match-end confirmation below. Undoing a point also undoes its auto-pause; editing a match (1.8) can correct the recorded time.
- Display: a large clock on the court screen, a smaller one on the TV and the overlay, colors from theme tokens (M.11).

**Match-end confirmation** (in-app panel, not the browser's `confirm()`: it shows the name, points and next match with large tablet buttons, and works where native dialogs are blocked)

| Situation | Confirmation |
|---|---|
| 2nd point | "*Name* wins (M, K)" |
| 2nd hansoku gives the opponent their 2nd point | "*Name* wins (hansoku)" |
| Time up, 1–0 | "*Name* wins, 1–0 on time" |
| Time up, tied, draw allowed (pools, team bouts) | "Hikiwake: record a draw?" |
| Time up, tied, winner required (elimination, playoffs) | "Encho: start overtime?" (starts the encho clock) |
| Encho point | "*Name* wins in encho" |
| Hantei | "Hantei: who won?" [White] [Red] |
| Team bout decided | "Senpo: *Name* wins", then the next bout; at the end of the pairing "*Team A* wins 3–1" or the representative-match prompt |
| Kachinuki | "*Name* wins and stays in" |
| Fusen-gachi | Its existing dialog, unchanged |

- Buttons: **Next match** (today's Next Match), **Undo last point** (the wrong-side mistake), **Keep scoring** (close). Nothing advances without a tap.
- Optional per tournament (on by default?), for scorekeepers who prefer today's manual flow.
- TV and overlay may show "WINNER: *Name*" briefly after the tap, before the next match.

**Sound**
- Time-up whistle/buzzer on the court device; optional cues (30 seconds left; a chime on the TV when a new match starts).
- Browsers play sound only after a tap on the page: the court screen enables sound on its first tap (or a one-time "Tap to enable sound" at the start of the day). Sound on/off per device (a TV in a quiet hall may not want it). A visual flash at time-up in case sound is muted. Test iPad silent switch/volume and a Bluetooth speaker per court.

**Order**
1. 1.5 match timing settings (also used by the program, 1.7).
2. Court timer, local only: clock, kendo rules, match-end confirmation (from scoring and from time-up).
3. Timer on TV and overlay (start/stop messages), optional winner display.
4. Sound on the court device, then optional TV cues.
5. 1.1 / 1.2 auto-advance and running order (control-desk direction).

Works with today's sync; when action-based sync lands (Phase 3), timer events become ordinary actions.

Questions for the meeting: how timekeeping works at events today (separate timekeeper, stopwatch?); auto-pause on a point or not; encho unlimited or fixed; confirmation on by default.

### After the React screens: the remaining architecture

When M.13 is done, React draws every screen, but the legacy classic script still *decides* (which match is current, what a court shows next, applying engine plans to `state`) and *stores* (one mutable global `state`, saved and synced as a whole). The goal is a layered app in which the rules, the decisions and the storage each have one home:

| Layer | Job | Today |
|---|---|---|
| Engine (`app/engine/`) | Pure tournament rules: pools, standings, brackets, teams, integrity, generation | ✅ done (2.0–2.7) |
| **Command / service layer** | One function per user action (`scorePoint`, `nextMatch`, `undo`, `editPool`, `regenerateDivision`, `setAward` …): check it is allowed, call the engine, return the change as data (an action/patch), never touch the DOM | Spread over legacy functions that mutate `state` and redraw |
| **Store** | Tournament data (shared, synced) separate from device/screen state (local: current court, open view, selections); typed; React subscribes with selectors | One global `state` mixing both (2.8) |
| UI (React) | Draws from the store, sends commands | ✅ screens done (M.8, M.13), reading published data |
| Sync adapter | Sends commands/actions to the server, receives others', handles offline queue and conflicts | Whole-snapshot saves, outbox, rebase (`18-`/`20-`/`21-`/`33-`) |

The command layer is a "service" in the sense of a single entry point for every change, not necessarily a separate server: it runs in the browser, and with Phase 3 the same commands can run on the server (the tournament's Durable Object) as the official copy, which makes conflicts and the outbox much simpler (actions are replayed, not whole snapshots merged).

**Store options (decide with the framework question at the meeting).** The pattern is settled: commands become serializable actions, a reducer applies them using the engine, the store holds tournament data separate from device/screen state, React reads it through selectors. KSM is halfway there already (court actions are recorded as `patch-v1` changes with who/when; the engine is pure; the islands use `useSyncExternalStore`). The reducer must be framework-free so the same code can run on the server (the tournament's Durable Object) in Phase 3.

| Option | For | Against |
|---|---|---|
| **React's own APIs: a plain reducer + store module outside the components, connected with `useSyncExternalStore`** (recommended) | Only React's official, supported mechanism (the one Redux and Zustand use underneath); no new dependency; legacy code can read and update it during the migration; the reducer runs on the server too; fits what the islands already do | We write and maintain the small store; no devtools out of the box |
| `useReducer` + Context (state inside the React tree) | Also React-only | Legacy code and the server can't reach it; every consumer re-renders on each change (TVs, tablets); not suitable for the shared tournament state |
| Redux Toolkit | Widely used, good docs and devtools (action log, time travel: "what happened on Court B?") | A separate project, not part of React; more ceremony; Immer-style updates must stay serializable for sync |
| Zustand | Very small | Little structure for actions; the action log would be ours anyway |

Recommendation: start 2.8 with the React-only option; actions and reducers carry over unchanged if Redux Toolkit's devtools are wanted later.

### Login and permissions: proposal (for the meeting)

Today: one shared staff password per tournament (4 characters minimum), stored as an unsalted SHA-256 hash in the Durable Object, sent with every save (`x-ksm-session-key`) and kept in `sessionStorage`; no limit on login attempts; the login is a browser `prompt()` (some embedded/kiosk browsers block it, e.g. the Claude browser pane).

Two separate questions: **who are you** (authentication) and **what may you do** (authorization, always checked by the Worker on every write; the UI only hides what a role can't use).

| Who | Authentication | Authorization |
|---|---|---|
| Directors / admins (a few HKF people) | **Cloudflare Access** (email one-time code or Google; free for a small team, confirm limits). Cloudflare sets the `CF_Authorization` cookie and forwards a signed token (`Cf-Access-Jwt-Assertion`); the Worker verifies it against the account's Access public keys | KSM's own per-tournament role list in the Durable Object (Access knows who, not "directs this tournament") |
| Court tablets | **Device pairing** in KSM: the director shows a short code / QR, the tablet exchanges it for its own token (tournament + court), revocable, expires after the event | The token's scope: that tournament, that court; can't edit Setup or score another court |
| Spectators / TVs | None | Read-only (or the visibility the meeting decides) |

- The front end calls `GET /api/me?tournament=<id>` → `{ email, role, court }` and shows the views for that role; every save is re-checked by the Worker.
- Access protects hostnames/paths (e.g. admin paths), not tournaments, so it pairs with M.9 path URLs; it needs the app on a domain in the HKF-owned Cloudflare account (hosting decision first).
- Offline/PWA: when an Access session expires, API calls are redirected to Cloudflare's login page; the app must detect it and show "sign in again", the service worker must never cache that page as the app, and work scored meanwhile stays queued (outbox, F6) until sign-in.
- Useful now, whatever is chosen: an in-app login dialog instead of `prompt()`, a limit on login attempts, a salted slow hash (PBKDF2 in Workers), a short-lived session token instead of the password on every save.
- **Device identity must be part of this decision.** Today each browser makes up its own device ID once (`ensureClientIdentity()`, `app/js/20`: `crypto.randomUUID()`, kept in local storage). Saves, court actions and the live connection carry it: a staff device uses it to ignore its own echoed save, the conflict rebase replays only the actions with this device's ID (F4, F6 rely on it), and presence lists devices by it. Limits: it identifies a browser, not a device or a tab (a staff tab and a TV tab in one browser share it; the code has a special case for that); clearing site data makes a new identity; it proves nothing (any device can claim any ID); and `crypto.randomUUID()` exists only on secure pages (https or localhost), so on a plain `http://` address startup fails before the device has an ID. Proposal: the identity comes from the server with the login, i.e. the device-pairing key (court tablets) or the signed-in director's session is the device's identity (unforgeable, revocable, tied to role and court), plus a per-tab ID in `sessionStorage` for recognising the tab's own saves. Then `crypto.randomUUID()` is no longer needed for identity. Not fixed on its own before the login decision (the deployed site is https).

### Backups and replacing Save/Load (for the meeting)

Today the only cloud storage is one Durable Object per tournament (`TournamentState`, SQLite); there is no automatic backup, and docs/CLOUD_OPERATIONS.md asks staff to download a `.ksm` file before the event. Proposal: backups happen by themselves, and Save/Load leaves the main navigation.

1. **Version history in the tournament's Durable Object**: restore points as SQLite rows at generation, end of pools, each bracket stage and the final, plus the last N saves. A director picks one and restores it (e.g. "before Regenerate Single Division"). Lost if the object itself is reset or deleted, so not a backup on its own.
2. **Cloudflare point-in-time recovery** of SQLite-backed Durable Objects (currently about 30 days; confirm limits): whole-object restore for disasters, operated by an admin.
3. **Off-object copies in R2** (new bucket binding, e.g. `KSM_BACKUPS`): the Worker writes a JSON export at each stage point and a final archive (`tournaments/<id>/<stage>-rev<N>.json`), with lifecycle retention. Survives an object reset, a bad deploy or a bad save. Restore = admin import into a new or existing tournament; practise it (restore drill) before the first event that relies on it.
4. **Outside Cloudflare**: the final archive (with the program, 1.7) downloadable or sent elsewhere, in case of account-level loss.

Then: **Export / Import tournament** stays as a deliberate admin tool (Setup / Director), not the main nav; the **recovery file** becomes a Developer Tools diagnostic once action-based sync removes conflict losses; for events with no internet at all, devices keep queued work in IndexedDB (local-first) instead of anyone passing files around (today's outbox holds only one snapshot). The 0.5 guard is needed until then.
